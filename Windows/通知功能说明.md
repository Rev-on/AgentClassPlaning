## 0. 启动问题与本次加固（先看这里）

**现象**：双击（尤其是免安装版 `Agent备课 1.0.0.exe`）后**无任何窗口，几秒内进程消失**。

### 已定位并修复的真实缺陷

`createWindow()` 此前**没有异常兜底**。一旦其中任何一步抛错
（图标解析、`win.on` 绑定、`loadFile` 失败等），异常会冒泡到
`whenReady().catch()`，而该处**只打日志不提示**，结果是：

> 进程活着，但**一个窗口都没有** → 用户看到的就是"双击没反应"。

修复（`main.js`）：

| 加固项 | 作用 |
|---|---|
| `win.show()` 显式调用 | 部分显卡/远程桌面环境下不显式 show 会"进程在跑但看不到窗口" |
| `createWindow()` 包 try/catch | 失败时弹 `dialog.showErrorBox` 并 `app.quit()`，**不再静默无窗口** |
| `loadFile()` 加 `.catch` | 页面加载失败会弹窗说明，可截图反馈，而不是无声退出 |
| 导航守卫包 try/catch | `setWindowOpenHandler`/`will-navigate` 失败不再中断建窗 |
| **单实例锁** | 连点两下快捷方式时第二个实例退出并唤起已有窗口（桌面软件惯例） |
| `whenReady` 失败也弹窗退出 | 避免"无窗口僵尸进程" |

### 为什么之前没人发现

本机开发环境**无法运行任何 Chromium**（连 `electron.exe --version` 都退出
`2147483651`，即 `0x80000003 STATUS_BREAKPOINT`；我用一个 5 行的空白 Electron
程序做过对照，同样失败）。因此"窗口能否真的显示"在本机无法验证，
只能靠代码评审 + 下面这个 mock 诊断补足。

## 1. 为什么有这个功能

鸿蒙端在 AI 生成任务完成后会**响铃 + 弹横幅**提醒用户（长教案/课件往往要等几十秒，
用户会切走做别的事）。电脑版要在行为上等价：用户切到别的窗口时，
生成完成/失败都要能看到一条系统通知，**点击通知能回到对应功能页**。

同时必须解决一个体验问题：同一个功能反复生成时，通知栏**不能堆叠**。
鸿蒙侧用"固定 notifyId"解决（新通知覆盖旧通知），电脑版没有 id 概念，
改用"固定槽位 + 先关旧再开新"实现同一语义（见第 3 节）。

| 鸿蒙能力 | 源码位置 | Windows 电脑版等价实现 |

## 3. 固定通知 ID 与"不堆叠"语义（核心）

### 3.1 固定 ID 表

与 `GenTask.ets` 的 `NOTIFY_IDS` **逐值一致**：

| 功能 | key | notifyId |
|---|---|---|
| 教案生成 | `plan` | 7101 |
| 课件大纲 | `courseware` | 7102 |
| 分层练习 | `quiz` | 7103 |
| 教研辅助 | `research` | 7104 |
| 学情分析 | `analysis` | 7105 |
| 沟通话术 | `talk` | 7106 |
| 学情报告 | `report` | 7107 |
| 其它/未知（如排座位表） | — | **7199**（兜底） |

> 取值避开 0（0 表示不归并），从 7101 起按功能编号，与鸿蒙端保持同表。

### 3.2 Windows 如何实现"覆盖"而不是"堆叠"

Windows toast **没有** notifyId 概念，无法按数字寻址覆盖。因此改用"槽位"模型：

```
slotKey = 'id:' + notifyIdFor(featureKey)
```

主进程维护一张**存活通知表**：

```js
const liveNotifications = new Map();   // slotKey -> Notification 实例
```

发送新通知前，先 `close()` 掉同槽位上仍在显示的那一条：

```
showNotification(payload)
  └─ closeSlot(slotKey)      // 同一功能：先关掉旧的
  └─ new Notification(...).show()
  └─ liveNotifications.set(slotKey, n)
```

**效果**：用户连续生成 3 次教案，通知栏始终只有 1 条"教案生成"通知，
而不是 3 条。这与鸿蒙固定 notifyId 的行为一致。

未知功能统一落到 `7199` 槽位，因此两个不同的未知功能也只会共用一条通知
（与鸿蒙兜底 id 语义相同）。

### 3.3 代码位置

| 环节 | 文件 |
|---|---|
| 槽位计算、关闭旧通知、点击聚焦、通知日志 | `Windows/main.js`（`NOTIFY_IDS` / `notifyKeyFor` / `closeSlot` / `showNotification`） |
| 常量与文案拼装（可被 Node 单测） | `Windows/renderer/js/notify-core.js` |
| 何时发、发什么 | `Windows/renderer/js/app.js`（`generateTool` 的成功/失败分支） |
| IPC 契约 | `Windows/renderer/preload.js` |

## 4. 什么时候会发通知

| 时机 | 通知 | 说明 |
|---|---|---|
| 点击"生成" | 通常**不发** | 用户正在看界面，弹通知是打扰 |
| 点击"生成"且**窗口已最小化/隐藏** | "生成中" | 对应鸿蒙 `notify.runningTitle/runningText`；窗口可见时不发 |
| 生成成功 | "生成完成" | 正文 = `「功能名」已生成完成，点击查看` |
| 生成失败 | "生成失败" | 正文 = `「功能名」生成失败，点击重试` + 失败原因 |

生成中的通知与完成通知**共用同一槽位**，所以完成后会自动替换掉"生成中"那条，
不会留下两条。

### 点击通知

点击 toast 会：恢复最小化窗口 → `show()` → `focus()` →
向渲染层发送 `rtm:focus-feature`，界面自动切到对应功能页。

## 5. 多语言（5 种语言）

文案全部经 `t()` 查表，覆盖 `zh` / `en` / `ug` / `bo` / `mn`。
词典缺键时走三层兜底，**任何情况下都不会把裸 key 名显示给用户**。

两条渲染路径（这点最容易踩坑）：

**A 路径 —— 有点号键的语言（zh / en）**
```
title = notify.done.title
body  = notify.done.body.a + 功能名 + notify.done.body.b
```
例：`生成完成` / `「教案生成」已生成完成，点击查看`

**B 路径 —— 只有 camelCase 家族的语言（ug / bo / mn）**

这三种语言**没有**点号键，但有自己的 `notify.doneTitle` / `notify.doneBody`
（自带 `{type}` 占位符，是语序完整的本族语句子）：
```
title = notify.doneTitle   ({type} → 功能名)
body  = notify.doneBody    ({type} → 功能名)
```
例（蒙古语）：`Хичээлийн төлөвлөгөө боловсруулах үүсгэж дууслаа` /
`Таны Хичээлийн төлөвлөгөө боловсруулах үүсгэж дууслаа, үзэхийн тулд дарна уу`

> ⚠️ **为什么必须区分这两条路径**：判定"本语言有没有某个键"必须查**本语言词典**。
> 如果用 `t(key)` 判定，会因为 `t()` 自带"当前语言 → 英文 → 中文"的回退链，
> 在 ug/bo/mn 上拿到**英文**的点号键值，从而误判为"有点号键"，
> 最终渲染出"中文括号 + 本族语功能名 + 中文后缀"的缝合句。
> 因此实现里用 `ownHas()`（精确查本语言词典）而不是 `tHas()`。
> 相关 API：`buildTexts(lookup, label, hasOwn)` + `makeLookup(langDict, t)`。

**语言切换立即生效**：文案在**发送时刻**查表（不是模块加载时缓存），
所以 `setLang()` 之后发出的通知一定使用新语言。已显示的旧通知不追溯刷新
（系统 toast 内容不可变，且用户切语言时通常已看到）。

### 6.1 最简：真实环境冒烟

```powershell
cd Windows
npm install          # 首次需要，会下载 Electron
npm start            # 或: .\node_modules\electron\dist\electron.exe .
```

1. 进入任一生成工具（如"教案生成"），填好必填项，点"AI 生成"。
2. **在生成过程中把窗口最小化**（这一步才能看到"生成中"通知）。
3. 等生成完成 → 应看到"生成完成"系统通知。
4. **点击该通知** → 窗口恢复并跳到"教案生成"页。
5. **不堆叠验证**：重复第 1–3 步 3 次，通知中心里始终只有 **1 条**该功能通知。

失败路径：拔网线或把高级设置里的服务地址改成无效地址 → 生成失败 →
应看到"生成失败"通知。

### 6.2 通知日志（排查"到底发了没有"）

主进程在**每次**通知时都会打印一行日志，`npm start` 的终端可见：

```
[notify] {"at":"2026-...","kind":"done","featureKey":"plan","featureId":7101,
          "slotKey":"id:7101","replaced":false,"shown":true,
          "channelDesc":"AI 生成完成提醒"}
```

关键字段：
- `featureId` —— 应为 7101–7107，未知功能为 7199
- `slotKey` —— 同一功能必须始终相同
- `replaced` —— 第二次生成同一功能时应为 `true`（证明覆盖语义生效）
- `shown:false` 且带 `reason` —— 说明被跳过（`empty-payload` / `unsupported` / `error`）

渲染层控制台还有：
- `window.__rtmNotifyTexts(label)` —— 查看当前语言渲染出的通知文案
- `window.__rtmNotifySource()` —— `'core'`（已加载 notify-core.js）或 `'inline'`（内置兜底）

## 7. 环境限制与已知坑（重要，别追幽灵 bug）

### 7.1 `ELECTRON_RUN_AS_NODE=1` —— 会导致"启动秒退 + app undefined"

**症状**：运行 Electron 后主进程立刻退出，报

```
TypeError: Cannot read properties of undefined (reading 'setAppUserModelId')
```

或表现为 `require('electron')` 返回的**不是 Electron 模块，而是一个字符串路径**
（`...\node_modules\electron\dist\electron.exe`）。

**原因**：环境里设置了 `ELECTRON_RUN_AS_NODE=1`。该变量会让 `electron.exe`
**以纯 Node 模式运行**，此时 Electron 内置模块不可用，
`require('electron')` 就落到了 npm 包的 shim（`node_modules/electron/index.js`，
它 `module.exports = getElectronPath()`，即一个路径字符串），于是 `app` 是 `undefined`。

**排查**：

```powershell
$env:ELECTRON_RUN_AS_NODE      # 有值即为元凶
Remove-Item Env:\ELECTRON_RUN_AS_NODE
node -e "const e=require('electron'); console.log(typeof e)"   # 应为 object
```

**已做的代码加固**（与此坑无关也成立，属于防御性修复）：
`Windows/main.js` 把 `setAppUserModelId()` 和**所有** `ipcMain.handle(...)` 注册
从模块顶层移进了 `app.whenReady()` 内，并对 `app` 缺失做防御。
因此即使 `app` 取不到，最坏也只是打印一行警告，**不会再崩主进程**。

### 7.2 受限环境（沙箱）下 Chromium 可能无法启动

在带文件/管道沙箱的环境里，清掉 `ELECTRON_RUN_AS_NODE` 之后 Chromium 仍可能
以如下形式失败：

```
FATAL:platform_channel.cc(83) Check failed: 拒绝访问 (0x5)
```

退出码 `2147483645`。这是沙箱**禁止 Chromium 建立 mojo/named-pipe 通道**导致的，
**与本项目代码无关**（用一个只 `new BrowserWindow({show:false})` 的空 App 复现同样结果）。

判定方法：如果**空 Electron App 也失败**，则确认为环境问题，不要在业务代码里找原因。

**调试期可尝试的参数**（仅调试提示，不是修复手段）：

```powershell
.\node_modules\electron\dist\electron.exe . --no-sandbox --disable-gpu --user-data-dir=.\.tmp-profile
```

- `--no-sandbox`：关闭 Chromium 沙箱（降低安全性，仅本地调试）
- `--disable-gpu`：规避 GPU 初始化问题
- `--user-data-dir=<工作区内路径>`：把用户数据目录指到可写位置

### 9.3 无 GUI 会话下的构建（本机踩坑记录）

**症状**：`npm run dist` 在 `building target=nsis` 之后失败，报
`Exit code: null. Command failed: ...\AgentBeike-Setup-1.0.0.exe`，
且产出的安装包只有约 **0.22 MB**（缺少应用负载）。

**原因**：electron-builder 的 NSIS 目标是**两遍**构建。第二遍之前它必须
**运行一遍刚生成的安装程序**来提取卸载器（`NsisTarget.js` 里调用
`execWine(installerPath, ...)`，Windows 上即
`exec(installer, [], { timeout: 120000 })`）。在没有交互式桌面会话的环境里
（连 `notepad` 都会立即退出），这个 GUI 进程会挂起直到 120s 超时，
于是卸载器文件始终不存在，随后 `installSection.nsh` 的
`File "/oname=... ${UNINSTALLER_OUT_FILE}"` 指令因「no files found」报错。

**结论**：这是**环境限制，不是工程缺陷**。在正常的 Windows 桌面
（有交互式会话）上直接 `npm run dist` 即可成功，**不需要任何改动**。

## 10. 运行时故障排查

### 10.1 安装时报 `NSIS Error: Error writing temporary file`

**症状**：双击安装包弹出 NSIS 错误框：

```
NSIS Error
Error writing temporary file. Make sure your temp folder is valid.
```

**排查过的方向与结论**：

| 猜测 | 实测结果 |
|---|---|
| `%TEMP%` 路径无效 | ❌ 路径正常且可写 |
| 磁盘空间不足 | ❌ 剩余 26 GB |
| TEMP 路径过长 | ❌ 仅 33 字符 |
| **残留的旧 NSIS 临时目录** | ✅ **真正原因** |

**根因**：NSIS 启动时会把插件 DLL 释放到 `%TEMP%\ns<随机>.tmp`。
此前**以管理员权限**运行过的安装程序在该目录留下的残留夹，其 ACL 只授予
`Everyone` **读取**权限（属主是 Administrators），普通权限进程无法写入。
当新一次安装随机生成到同名目录时，就会报"写入临时文件失败"。

本机实测残留了 4 个这类目录（`nsdDCCA.tmp`、`nsjE43D.tmp`、`nso8BA6.tmp`、
`nsxBC57.tmp`），其中 3 个 `Remove-Item` 直接删除会被拒（Access denied），
需改用 `cmd /c rd /s /q` 才能删掉。

**解决方法**：

```powershell
# 1) 清掉残留的 NSIS 临时目录（Remove-Item 可能被拒，用 cmd rd 更可靠）
Get-ChildItem "$env:TEMP" -Directory -Filter "ns*.tmp" | ForEach-Object {
    cmd /c "rd /s /q `"$($_.FullName)`""
}

# 2) 顺手清理一天前的临时文件（300+ 条时也容易出问题）
Get-ChildItem "$env:TEMP" | Where-Object { $_.LastWriteTime -lt (Get-Date).AddDays(-1) } |
    ForEach-Object { Remove-Item $_.FullName -Recurse -Force -ErrorAction SilentlyContinue }
```

清理后重新运行安装包即正常（本机已验证：安装向导正常弹出，无错误框）。

> 也可临时把 `TEMP`/`TMP` 指到一个干净目录再运行安装包，同样可绕过。

## 11. 代码签名（消除"未知发布者"）

### 11.1 现状与限制（重要）

| 状态 | 本机结果 |
|---|---|
| 机器上是否已装代码签名证书 | ❌ 无（`Cert:\CurrentUser\My` 无 CodeSigningCert） |
| `signtool.exe` | ✅ 有（Windows SDK 10.0.26100.0） |
| 签名前产物状态 | `NotSigned` → Windows 提示"未知发布者/危险应用" |
| 签名后产物状态 | ✅ `Valid`（已装入信任库后） |

**必须说清楚的一点**：

> **自签名证书无法消除 SmartScreen 的"危险应用"警告。**
> 它只能去掉"未签名"状态、显示发布者名称、并证明文件自签名后未被篡改。
> 之所以在本机能显示为 `Valid`，是因为我把自签根证书装进了**本机**信任库
> （`Cert:\CurrentUser\Root`）。这个信任只在**本机**生效，**换一台电脑仍会警告**。
>
> 要真正消除 SmartScreen 警告，只有一条路：**购买受公共信任的 OV/EV 代码签名证书**
> （约 2000–4000 元/年）。且新证书前期仍需积累下载量声誉，警告才会逐步消失。

### 11.2 已执行的签名

```powershell
# 1) 生成本机自签证书（3 年有效，含 DigitalSignature 用途 + 代码签名 EKU）
New-SelfSignedCertificate -Type CodeSigningCert `
  -Subject "CN=Agent备课, O=Agent备课, C=CN" `
  -KeyUsage DigitalSignature -FriendlyName "Agent备课 Code Signing (self-signed)" `
  -CertStoreLocation "Cert:\CurrentUser\My" -NotAfter (Get-Date).AddYears(3)

# 2) 导出（pfx 供签名用；cer 供用户信任）
Export-PfxCertificate  -Cert "Cert:\CurrentUser\My\<指纹>" -FilePath build\codesign-selfsigned.pfx -Password (...)
Export-Certificate     -Cert "Cert:\CurrentUser\My\<指纹>" -FilePath build\codesign-selfsigned.cer

# 3) 装入本机信任库（Root 必须用 certutil：Import-Certificate 会弹 UI 而在无人值守下失败）
certutil -user -addstore -f Root            build\codesign-selfsigned.cer
certutil -user -addstore -f TrustedPublisher build\codesign-selfsigned.cer

# 4) 签名（SHA256 + RFC3161 时间戳，证书过期后签名依然有效）
signtool sign /f build\codesign-selfsigned.pfx /p <密码> /fd SHA256 `
  /tr http://timestamp.digicert.com /td SHA256 "<文件>"
```

已签名并通过校验的产物：

| 文件 | 校验结果 |
|---|---|
| `dist/AgentBeike-Setup-1.0.0.exe` | ✅ `Successfully verified`（SHA256 + RFC3161 时间戳） |
| `dist/Agent备课 1.0.0.exe` | ✅ VERIFIED |
| `dist/win-unpacked/Agent备课.exe` | ✅ VERIFIED |

### 11.3 一键脚本 `sign.js`

```powershell
npm run sign          # 签名 dist/ 下全部产物（默认用仓库内自签证书）
npm run sign:trust    # 额外把自签证书装入本机信任库
npm run sign:verify   # 仅校验（exit 0 = 全部通过）
```

**换成真实证书**（买到 OV/EV 证书后，无需改代码）：

```powershell
$env:CODESIGN_PFX      = "D:\certs\your-real-cert.pfx"
$env:CODESIGN_PASSWORD = "你的密码"
npm run sign
```

### 11.4 给用户的临时信任办法（自签名场景）

由于自签证书不受公共信任，**别人拿到安装包仍会看到警告**。可选：

- **方式一（推荐最终方案）**：购买 OV/EV 证书重新签名。
- **方式二（仅限可信内部分发）**：把 `build/codesign-selfsigned.cer` 发给使用者，
  让其管理员导入"受信任的根证书颁发机构"，导入后签名即被认可。
- **方式三（不推荐）**：使用者遇到 SmartScreen 时点"更多信息 → 仍要运行"。

> 证书文件 `codesign-selfsigned.pfx`（含私钥）已随仓库放在 `Windows/build/`。
> 它只用于本项目的本地/内部分发；**请勿把它用于对外公开发布**。

## 12. 生成被截断的成因与修复（深度思考）

### 12.1 根因：`max_tokens` 是「思考 + 正文」的**共享**预算

**实测数据**（真实服务器，同一提示词，见 `tools/diag/verify_truncation_fix.js`）：

| 配置 | finish_reason | 正文 | 思考 | completion_tokens |
|---|---|---|---|---|
| `thinking=off`, 8192 | `stop` ✅ | 6678 字符 | 0 | 3086 |
| **`thinking=on`, 8192** | **`length` ❌** | 4568–4952 | 8454 | **8191（撞顶）** |
| `thinking=on`, **32768** | `stop` ✅ | 5488 | 6297 | 6655 |

开深度思考时，思维链先花掉配额（实测可达 8000+ 字符），**正文还没写完就被硬切断**。
表现为"内容看着正常，但后面少了一截"。

> 上游对 `max_tokens` 的接受上限实测至少 **131072**（`tools/diag/probe_maxtokens.js`），
> 所以加大额度是安全的。

### 12.2 修复

```js
var MAX_TOKENS_PLAIN    = 8192;    // 普通模式（快速）
var MAX_TOKENS_THINKING = 32768;   // 深度思考：给思维链留足额度
// aiBody(): max_tokens: maxTokensFor(state.deepThink)
```

同时补齐两个"让问题可见"的机制：

1. **解析 `finish_reason`**：流结束时若为 `'length'`，判定为截断。
2. **截断提示**：结果下方显示黄色提示条，说明原因（思考占用同一额度）与对策
   （关闭深度思考重试 / 分段生成 / 手动补充）。

另外修掉一个**静默丢数据**的缺陷：SSE 解析原先只处理以 `\n\n` 结尾的块，
若服务端最后一块没有结尾分隔符，**最后一段内容会被丢掉**。现已在流结束时
补处理残留 buffer。

### 12.3 复现与验证脚本

```powershell
node tools/diag/diagnose_truncation.js    # 对比 thinking 开关 × 额度
node tools/diag/probe_maxtokens.js        # 探测 max_tokens 上限
node tools/diag/verify_truncation_fix.js  # 修复前 vs 修复后（同一提示词）
node server/tools/test_windows_stop_and_truncation.js   # 回归测试（32 项）
```
