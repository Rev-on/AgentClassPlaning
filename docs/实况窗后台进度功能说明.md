# 实况窗：后台实时显示 AI 生成进度

> 面向初中教学备课智能体（Agent备课 / Rev TechingMaster）
> 覆盖 7 大 AI 生成功能：教案 `plan`、课件 `courseware`、分层练习 `quiz`、
> 教研科研辅助 `research`、学情分析 `analysis`、沟通话术 `talk`、个性化学情报告 `report`

---

## 1. 功能是什么

用户在 7 个 AI 功能里点"生成"后，**按 Home 键或锁屏把应用退到后台**，
桌面（状态栏胶囊 / 锁屏 / 通知中心的实况窗卡片）会**持续显示生成进度百分比**，
进度条随生成推进而上升，而不是冻结在退出那一刻的数值。

生成完成、失败或用户主动停止时，实况窗自动收尾，不会残留。

---

## 2. 修复前的问题（为什么需要这次改造）

改造前的进度链路是**纯应用进程内回调驱动**的：

```
页面 SSE onDelta → LiveView.onContent(partial) → GenProgress.onLength
                 → liveViewManager.updateLiveView()
```

用户退到后台后，鸿蒙系统把应用进程置为**挂起（suspended）**状态，JS 引擎被冻结：

- 上述回调不再触发；
- 驱动回调的 `AiService.chatByTask`（SSE feed / 轮询循环）本身也依赖进程在跑。

**两个环节同时停摆 ⇒ `updateLiveView` 再也不会被调用 ⇒ 实况窗进度永久冻结。**
问题不在实况窗本身，而在于"驱动源在进程里"这个架构缺陷。

---

## 3. 解决方案：三条腿

### 腿 1 · 时间驱动的进度模型（地基）

`GenProgress` 从"回调次数驱动"改为 **`max(阶段锚点, 时间滑轨)`**：

| 组成 | 驱动源 | 说明 |
|---|---|---|
| 阶段锚点 | 回调 | 思考增量 → 12%；正文增量 → 基线 30 起，按 `已生成长度/预期长度` 推进到 95% 封顶 |
| 时间滑轨 | **仅 `Date.now() - startTime`** | 渐近曲线 `3 + 85·t/(t+45s)`，渐近 88%，SLA 兜底 150s→≥78% |

时间滑轨**不依赖任何回调**。进程被挂起期间滑轨当然不动（系统硬约束），
但**只要进程被重新调度**，下一次读取就按真实流逝时间把百分比一次性补齐 ——
观感上是"一直在走"，而不是卡死。

**为什么用渐近曲线而不是线性**：线性会超时后一路冲顶，过早显示 95% 反而误导；
渐近曲线前期增长快（刚切到后台就能看到数字在动）、后期收敛，
且**永远不会自己走到 100%**（只有 `onDone()` 能到 100）。

### 腿 2 · 后台短时任务（争取运行窗口）

只有腿 1 不够：若进程被无限期挂起，滑轨永远没有机会被读取。
因此生成开始时申请**短时任务**：

```ts
backgroundTaskManager.requestSuspendDelay(reason, callback)
```

- **不需要任何权限**：本地 SDK `@ohos.resourceschedule.backgroundTaskManager.d.ts:553`
  的函数声明处**没有 `@permission` 标注**（对比 `startBackgroundRunning:570`
  明确要求 `ohos.permission.KEEP_BACKGROUND_RUNNING` 受限权限）。`@since 9`，公开 API。
- 申请后应用**延迟进入挂起态**，系统在 `actualDelayTime` 内仍会让应用短暂运行。
- 于是退到后台这段时间里，**与页面完全解耦的看门狗定时器**（`setInterval` 2s）
  仍在跑，每拍：

  1. 按时间补齐百分比并 `updateLiveView` —— 实况窗**真的在实时动**；
  2. （节流 8s）拉服务端权威任务态，用真实产出长度抬高进度，并在服务端已
     `done`/`failed` 时**主动收尾**；
  3. 后台态下确保短时任务在手，额度将尽时续期（带 15s 节流防回调风暴）。

- 额度耗尽/申请失败（`9900001`/`9900002`）**静默降级**为腿 1 语义。

### 腿 3 · 生命周期接缝

| 回调 | 行为 |
|---|---|
| `EntryAbility.onCreate` | `LiveView.attach(this.context)` 注入 UIAbilityContext（SDK 要求系统代理在 UIAbility 身份下调用） |
| `EntryAbility.onBackground` | 标记后台态 + 确保看门狗 + 申请短时任务。**绝不结束实况窗** —— 退出后台不是"生成结束" |
| `EntryAbility.onForeground` | 立即补齐进度（把挂起期间"欠"的百分比补上）+ 释放短时任务额度 |
| `EntryAbility.onDestroy` | 释放定时器与后台任务 |

## 4. 为什么不用长时任务 / 服务端推送进度

**不用长时任务 `startBackgroundRunning`**：
- 它是**受限权限** `ohos.permission.KEEP_BACKGROUND_RUNNING`，需在 AGC 单独申请、
  审核严格，还要在 `module.json5` 声明 `backgroundModes`；
- 它会**常驻一条系统通知**（"应用正在后台运行"），而本应用的完成通知已由
  Push Kit 负责，再加一条属打扰；
- 本场景是"生成中的短时进度展示"（几十秒~几分钟），短时任务 + 时间滑轨已足够。
- ⇒ 因此**不需要改 `module.json5`、不引入任何新权限**。

**客户端不做周期性 Push 进度推送**：客户端无 Push Kit 应用内消息权限；
自建服务端发数据消息需应用在前台才展示。

> 注：服务端**确实**会在任务进行中补推进度（见第 5 节），
> 但那是"进程被杀后的兜底通道"，不是主通道。

---

## 5. 服务端补推（进程被杀/挂起时的兜底）

任务在**服务端队列**里执行，不受客户端进程生死影响。
客户端进程被杀后本地 `updateLiveView` 链路断掉，此时由服务端接管：

1. 客户端拿到 `taskId` 后调 `POST /api/task/:id/liveview` 上报
   `activityId` + `event` + 可选 `totalChars`/`expectedMinutes`；
2. 服务端在流式生成的 flush 心跳里，用**与客户端完全相同的公式**算百分比，
   经节流（单任务最小间隔 10s、上限 30 条）下发
   **push-type 7 / operation 1**，系统直接刷新实况窗，**无需 App 进程**；
3. 任务完成前先 `await` 一次最终进度，再发 **operation 2** 结束实况窗。

**为什么 `activityId` 必须由客户端自己生成**：SDK 的 `LiveViewResult` 只返回
`resultCode`/`message`，**不含任何 id**（`liveViewManager.d.ts:1416`），
系统不会告诉我们它分配了什么标识。因此客户端用 `Date.now() % 2147483647`
自生成正整数 id，服务端原样回传。

### 跨端进度一致性（重要）

服务端补推与客户端看门狗**交替更新同一个实况窗**，因此两端的百分比公式
**必须逐点一致**，否则后写的一方会把进度条**往回拉**。

这一条在本次开发中踩了两次坑，已用三层断言锁死：

| 层 | 断言内容 |
|---|---|
| 数值层 | `ANCHOR_THINK=12` / `ANCHOR_BODY_MIN=30` / `CAP_RUNNING=95` / `RAMP_START=3` / `RAMP_ASYMPTOTE=88` / `RAMP_TAU_MS=45000` / `SLA_FLOOR_*` 逐项跨端相等 |
| 行为层 | 真跑 `push.estimatePercent` 与客户端公式，在 7 类型 × 多长度 × 有/无思考 × 多时间点全网格比对（容差 ≤1pp） |
| 根因层 | `RAMP_ASYMPTOTE(88) < CAP_RUNNING(95)` —— 保证时间项永远无法把已抬高的回调锚点拉回去 |

> **两个已修复的历史缺陷（勿回退）**
> 1. **5pp**：服务端正文分支基线用 25，且**无条件覆盖**了思考锚点 12 ——
>    而客户端正文基线是 30。已改为 `max(思考锚点, 正文锚点)` 合成。
> 2. **26pp**：服务端曾按 `expectedMinutes` **缩放**流逝时间再喂给时间滑轨，
>    而客户端用的是**绝对流逝时间配固定 45s 时间常数**。两端根本不是同一个钟
>    （t=150s：服务端 52% vs 客户端 78%），方向是服务端落后，同样造成回拉。
>    已改为直接传原样 `elapsed`。
>    ⇒ **`expectedMinutes` 现已不参与百分比计算**，服务端仅记录用于诊断。
>    **不要为了"拟合"而填凑数值。**
>
> 修改 `GenProgress` 里那些常量，等于**修改跨端契约**，
> 必须同步 `server/src/push.js` 并重跑两套测试。

## 6. 进程被杀后的四级兜底

| # | 机制 |
|---|---|
| ① | 服务端任务在云端队列继续跑完（不受客户端生死影响） |
| ② | 任务结束后端发 push-type 7 / operation 2 结束实况窗，**不会残留"生成中"** |
| ③ | `GenTask.recover()` 下次启动时静默把结果补进历史 |
| ④ | `startLiveView` 传 `lifeCycleMode = AUTO_STOP_WHEN_APP_TERMINATE`，系统终止进程时直接收起实况窗 |

## 7. 容错原则

实况窗是**锦上添花**，任何失败都只写 `hilog`、绝不抛出、绝不阻塞生成主流程：

- 实况窗开关关闭 / 权益未申请 → 跳过，生成照常；
- `updateLiveView`/`startLiveView` 失败 → 只记日志；
- 短时任务配额耗尽 → 静默降级为时间补齐；
- 后台网络失败 → 静默（后台省电是常态），下次节拍再试；
- AGC 凭据未配置 → 服务端一条报文都不发，**零网络请求**。

### 安全边界（服务端）

- `event` **绝不发 `'PROGRESS'`** —— 它是**布局类型**（`LAYOUT_TYPE_PROGRESS`），
  不是**场景名**，传它会被华为拒收（`80100003`）。
  合法场景为 `TIMER`/`RENT`/`WORKOUT`/… （客户端 `EVENTS` 依次试探 14 个）。
- `activityId` 无效 / token 缺失 / 凭据未配置 → **一条报文都不发**。
  华为对"activityId 不存在"会**限用该 id 24 小时**，宁可少发不可乱发。
- 成功判定必须解析 **`body.code === '80000000'`**，不能只看 HTTP 200
  —— 华为**业务失败也返回 HTTP 200**。

## 10. 待真机验证（本地无法消除）

自动化测试**不能**证明华为侧对实况窗报文的接受度。上真机请验证：

1. 开一次较长生成（如教案）→ 按 Home 退到后台 →
   **观察进度条是否单调上升、有无回跳**；
2. 观察服务端补推（10s）与本地看门狗（2s）**交替更新时是否跳变**；
3. 若失败，服务端日志会打出
   `[push] 实况窗消息失败 operation=1 code=... body=...`（含完整响应体）。
   重点核对 `notificationData.richProgress` 与 `capsuleData.progressData`
   的**字段名与枚举取值**是否被接受；若被拒（`80100003`/`401`），
   按 body 报错定向删除对应子块即可，**进度更新本身不受影响**（其余字段照常下发）。

> `rejectedFields` 标记位已在 `/api/task/:id/liveview` 路由中落地，
> 便于线上区分"到底发的是哪一版报文"。

### 其他前置条件

- AGC 需开通**实况窗权益**（否则 `startLiveView` 返回 `1003500005`）；
- 系统与应用的实况窗开关需为开启（否则 `1003500004`）；
- 服务端 `PUSH_ENABLED=1`（**进度补推与完成通知共用此总开关**；
  生产环境已是 1，无需新增配置）。"服务端补推没生效"时先查这个开关。

## 11. 设计取舍速查

| 决策 | 取舍 |
|---|---|
| 短时任务而非长时任务 | 免权限、无常驻通知，合规成本最低；超长生成 (>10min) 的后台实时性受限 |
| 渐近曲线而非线性 | 不提前显示 95%，避免误导；代价是百分比不严格反映真实产出比例 |
| 时间滑轨而非纯回调 | 后台不冻死；代价是后台显示"约 N%"（明示为估算值） |
| 两端同公式而非各算各的 | 交替更新不跳变；代价是常量成为跨端契约，改动需同步 |
| 客户端自生成 activityId | 服务端才能结束实况窗；代价是需自行保证正整数且唯一 |
| `AUTO_STOP_WHEN_APP_TERMINATE` | 进程被终止时不留残留；代价是终止即收起（由服务端 push 补收尾） |
